# 音声判定の調査・評価・次の改善

## 今回の範囲

v8.6の全HTML/JavaScript、manifest、README、references.jsonの構造と13件の内容、および内蔵MP3のデコード結果を確認した。アプリが実際に使っているのは `EMBEDDED` の13本のMP3で、`references.json` は読み込まれていない。READMEの「数値特徴のみ」は現状と一致していない（既存のREADME編集を保護するため、このPRでは変更しない）。内蔵基準は動画から推定区間を切り出したものと記載され、正解ラベル・鳴き声区間を人が確認する必要がある。

手元に独立したiPhoneマイク録音や登録サンプルJSONはない。ユーザーから、iCloud Driveに鳴き声サイトをiPhoneで画面録画したデータがあると回答を得た。画面録画は基準の区間・ラベル確認に有用だが、デジタル音声の画面録画だけでは、スピーカー→室内→iPhoneマイクの変化を評価できない。録音元は https://pokearcade.jp/エクストレジャー2弾-鳴き声/ 、使用端末はiPhone 16 Pro、画面録画のマイクはオンとの回答を得た。サイトへの接続は環境のネットワーク制限で403となり、音源構成は未確認。マイクオンの画面録画には内部音声とマイク音声が混ざる可能性があり、元ファイルを確認する必要がある。共有されたファイルは別途検証する。内蔵音声の自己照合結果を実録音の判定精度として扱わない。

## 現行方式の問題

- 8 kHzへ線形補間でリサンプリングする。4 kHz以上の情報を落とすうえ、アンチエイリアスのローパス処理がない。
- 64 ms窓、32 ms間隔、24個の対数間隔帯域の対数パワーをフレーム内で中心化・正規化する。MFCCではない。`log(1+power)` は小音量で音量変化に対して完全には不変でない。
- 照合は5通りの一定の速度倍率で線形対応させる。鳴き声の部分ごとの伸縮には対応しない。粗い探索間隔により一致区間を外す可能性もある。
- 3秒の窓が有効フレーム55%以上であること、3分割した各区間の有効フレーム数などを要求する。短い鳴き声＋長い無音では、正しい基準自身でも照合が成立しない。人の声も有効フレームになり、鳴き声との区別はない。
- 全候補の最大値を採用するため、登録数が多いクラスは高い最大値を得やすい。追加録音と内蔵MP3の指標も、異なる録音条件に対して校正されていない。
- 0.03の僅差表示は未校正。全候補が低品質でも相対順位が付く。未知音、人声、雑音の棄却を評価していない。
- 保存時に先頭180フレームだけを保持していた。長い区間を登録すると後半の鳴き声が失われ、使用者には分からなかった。

今回の修正は全クラス共通の2点のみ：探索グリッドから外れた末尾の候補も比較する、180フレームを超える登録区間は黙って切らずエラーを表示する。旧保存キー、旧180フレーム以内のデータ、JSON形式を維持する。過去に切り捨てた音声を特徴JSONから復元することはできない。

## 方式比較と選択

| 方式 | iPhoneブラウザでの実装 | 長所 | 検証すべき点・判断 |
| --- | --- | --- | --- |
| 現行スペクトル＋一定倍率 | 既存のWeb AudioとJavaScript | 軽量、旧データ互換 | 録音条件と局所的な時間変化に弱い。検証済みの標準方式として当面維持 |
| MFCC＋DTW | Web Audio、FFT、軽量JavaScript。実験用コードを追加 | 音色と時系列を扱う。c0を除いて音量への依存を減らし、局所的な時間対応を試せる | 人声を自動で除ける訳ではない。今回は速度変更・雑音で現行より悪化し、不採用 |
| log-mel＋DTW／デルタ特徴 | 同様に実装可能 | MFCCで捨てる帯域詳細や変化率を比較できる | ラベル付き録音を揃えた後の次候補。旧特徴だけから正確には再生成できない |
| 音声埋め込み（YAMNet等） | TensorFlow.jsまたはONNX Runtime Web。モデルの配信とSafari検証が必要 | 録音条件に対して頑健な表現を得られる可能性 | 一般環境音モデルはポケモン13種を学習していない。音声モデルの選択、クラス用の学習・評価、配信容量、メモリ、起動時間を測定する必要がある |

現実的な最初の評価候補は小規模なMFCC／log-mel＋DTWで、ニューラルモデルへの移行は独立録音の比較結果で決める。`tools/mfcc-dtw.js` は評価専用で、アプリから読み込まない。8 kHz、25 ms窓、10 msホップ、24三角melフィルタ、c0を除く13係数、正規化、端の低エネルギー区間の除去、部分系列DTWの試作である。経路の時間長制約や複数テンプレートの集約は未校正であり、本番利用の完成版ではない。

## 再現可能な検証

Node.js、Python 3、Chromiumを使用。ブラウザテストにはplaywright-core 1.58.2を使った。アプリの依存関係は増やしていない。

```sh
npm install --prefix /tmp/frienda-eval --cache /tmp/frienda-npm-cache --no-audit --no-fund --save-exact playwright-core@1.58.2
export NODE_PATH=/tmp/frienda-eval/node_modules
node --test tests/audio.test.cjs
node tools/audio-evaluate.cjs '' /tmp/audio-report.json
```

評価ツールは自分で一時HTTPサーバーとブラウザを起動して終了する。外部への録音アップロードは行わない。各音声の推定ラベル、指標、2位との差、処理時間、ソースSHA-256をJSONに保存する。内蔵音声の最もエネルギーが高い1秒を機械的に選び、同じ区間に音量・速度・固定シードの白色雑音の変更を施す。分類が成功する区間を選別してはいない。

ブラウザ機能テストは別ターミナルでサーバーを起動して実行する：

```sh
python3 -m http.server 8000 --bind 127.0.0.1
# 別ターミナル、リポジトリルートで：
node tests/browser-smoke.cjs
node tests/browser-diagnostics.cjs
node tests/browser-recording.cjs
```

録音テストは仮想マイクを使用する。実機iPhoneのマイク・Safari互換性は検証していない。構文チェックはHTML内のscriptを抽出して `node --check` で確認する。

`audio-baseline.json` は修正前、`audio-current.json` は修正後。どちらも各条件13件。結果の「正解」は内蔵ラベルと一致したという意味で、音源ラベルそのものの正しさや独立録音の精度を保証しない。

| 入力条件 | 現行方式 | MFCC＋DTW試作 |
| --- | ---: | ---: |
| 内蔵MP3全体 | 11/13（2件照合不成立） | 13/13 |
| 最大エネルギーの1秒 | 13/13 | 13/13 |
| 同1秒、音量0.1倍 | 13/13 | 13/13 |
| 同1秒、再生速度1.1倍 | 13/13 | 11/13 |
| 同1秒、人工白色雑音10 dB | 13/13 | 12/13 |

この検証では末尾探索修正による13種の順位変化は見られなかった。独立した回帰テストでは末尾に置いた完全一致のスコアが修正前0.218→修正後1.000となった。これは探索漏れの修正を示し、実録音の精度改善とは別である。長い登録区間の無通知切り捨ても、修正前のテスト失敗から修正後の成功を確認した。

## 必要な実録音と評価方法

原因分析の開始には各クラス3〜5回の独立したマイク録音（計39〜65回）を用意する。特にアルセウスとマーシャドーの誤判定例と正解例を含める。方式選択・最終評価の次の目安は13匹×20回＝260回の独立したiPhoneマイク録音。各クラス5回をテンプレート、5回を開発検証、10回を最終テストとし、録音セッションを分ける。同じ録音の切り出し違いや加工違いをテンプレートとテストに分けない。全クラスで同じ手順・同じ条件数を使い、アルセウスだけを特別扱いしない。実際のプレイ環境で鳴き声を再生し、静かな環境、通常の周囲音、人声混入、距離・音量を変えた条件を含める。さらに鳴き声なし・人声のみ・環境音のみを各10回以上採取し、誤受理率を測る。件数は開始時の目安で、高精度を保証する条件ではない。

ファイルには正解名、録音ID、iPhone機種、iOS、マイク/画面録画の別、日時またはセッションID、再生元、距離、録音環境、鳴き声の開始・終了秒を対応付ける。画面録画の元ファイルは基準の確認用にも使う。旧追加録音JSONは現行方式の分析に利用できるが、MFCCや音声埋め込み用には元のM4A/WAV/MP4が必要である。

外部録音の評価用manifest例（データはリポジトリ外に置く）：

```json
{
  "recordings": [
    {"id":"arceus-ref-01","name":"アルセウス","session":"quiet-session-A","split":"reference","file":"ref-01.m4a","start":1.2,"end":3.4},
    {"id":"arceus-test-01","name":"アルセウス","session":"quiet-session-B","split":"test","file":"test-01.m4a","start":0.8,"end":3.0}
  ]
}
```

```sh
node tools/audio-evaluate.cjs /path/to/manifest.json /tmp/held-out-report.json
```

この例は形式を示す2件だけで、13種の評価として十分ではない。ツールはセッションIDと元ファイル内容のSHA-256によるテンプレート・テスト間の重複を拒否する。分割の真正性はデータ収集時に確認する必要がある。複数テンプレートはクラス内の最大値で評価する（現行と同じルール）。外部参照は現行の登録形式と同じ180フレーム以内に区間を指定し、丸め処理も揃える。開発検証と最終テストは別manifestで実行し、最終テスト結果で閾値を調整しない。全体正解率だけでなく、クラス別正解率、混同行列、棄却数を確認する。今回のツールは13種の閉集合の評価用であり、未知音の棄却評価や実機の遅延評価は次の段階で追加する。

## 次の優先順位

1. 画面録画を聞いて基準13本のラベル・区間を確認し、上記の実マイク録音を集める。アルセウス→マーシャドーの誤判定ファイルは、正解例と同じ条件で比較する。
2. データをセッションで分割し、クラス別・混同行列の基準値を確定する。開発用データで僅差・最低指標・鳴き声なしの棄却閾値を校正する。
3. 全クラス共通のアンチエイリアス、鳴き声区間抽出、MFCC/log-mel＋制約付きDTWを比較する。登録数の偏りに強いテンプレート集約と、長い録音・人声混入の扱いを検証する。改善しない方式を標準にしない。
4. 独立した録音で改善した方式をWeb Worker化し、iPhone Safariで初期化・録音・メモリ・判定時間を測る。旧データは残し、新特徴が必要な録音には再登録導線を用意する。
5. 上記方式の精度が不足する場合に音声埋め込み＋クラス用分類器を比較する。単純方式とのクラス別精度・棄却・実機負荷の差で採否を決める。

今回は「iPhoneで高精度に完成」とは言えない。再現可能な評価と2件の既知不具合修正が完了した段階であり、実録音が届いた後に独立録音の評価を継続する。
