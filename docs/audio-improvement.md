# 音声判定の調査・評価・次の改善

## v8.7の現在の結果と使い方

提供された13匹各1件のiPhoneマイク録音と、既存の内蔵13本のMP3を使って比較した。全13件で従来方式の1位がヌメルゴンになる症状を再現した。各クラス1件で、このデータを方式選択にも使っているため、以下は開発用録音に対する結果であり、独立した実使用精度ではない。

| 方式 | 正解数／13録音 |
| --- | ---: |
| 従来スペクトル照合 | 1 |
| 録音全体のMFCC＋DTW | 2 |
| 録音全体のMFCC平均補正＋DTW | 8 |
| 区間抽出＋MFCC平均補正＋DTW | 10 |
| 学習済みYAMNet埋め込み、平均／エネルギー重み付き | 2／4 |
| 学習済みYAMNet埋め込み、共通のピーク音量補正あり | 5／5 |

v8.7には「区間抽出＋MFCC/DTW（試験）」を追加した。初回は従来方式で起動し、判定方式の選択を次回にも保存する。全クラス共通のRMS閾値で録音を区間に分け、最大エネルギーの区間を入力とする。内蔵MP3の各区間と、対応する特徴を持つ追加録音をMFCCの時間平均補正・DTWで比較する。アルセウス専用処理やクラス別の閾値は設けない。実際に13件を画面から読み込んだ機能テストでも10/13だった。

試験方式で誤判定が残ったのはヒスイゾロアーク→ルカリオ、マーシャドー→ディアルガ、ラプラス→ルカリオ（44.1 kHzデコード）／パルキア（48 kHzデコード）。いずれも1位と2位の差が0.03未満で「判定不確か」と表示された。ただし正解したゲンガー・ヌメルゴン・ガブリアスも不確かと表示され、計6件。0.03は既存の未校正の基準であり、正解確率や誤判定の完全な検出を示すものではない。44.1／48 kHzとも正解数10・不確か6だったが、誤判定先が一致しないケースがある。Chromiumでの確認であり、iPhone Safari実機での性能・互換性は未検証。

録音・ファイル入力・手動区間指定・区間再生・基準MP3再生・登録数表示・内蔵／追加録音の個別指標・照合診断を維持した。試験方式の再生ボタンは比較候補として使った基準の抽出区間を再生する。DTWが対応させた正確な時間範囲を推定したものではない。録音全体に複数の鳴き声がある場合は最大エネルギーの区間が選ばれるため、目的の鳴き声を手動区間指定する。

### v8.5／v8.6の保存データ

既存の保存キー、旧特徴フレーム、JSONのversion=1は維持する。従来方式は旧登録をそのまま使う。試験方式では旧登録を「従来方式のみ」と診断表示し、照合しない。旧特徴だけからMFCCを復元できないため、試験方式で使う追加録音は元音声を読み込み、区間を指定して再登録する。新規登録は従来特徴と追加のMFCC区間特徴を保存し、両方式で利用できる。再読み込み・書き出し・復元を確認した。旧JSONをインポートすると現在の登録を置き換える既存動作は変わらない。原音声やモデル重みはGitHubに含めない。

### 症状の分析

各録音の最低RMSの1秒を共通ルールで選んで従来方式に入力すると、13件中11件でヌメルゴンが1位、1件でサザンドラ、1件で照合不成立だった。低音量区間でもヌメルゴンが高い指標を得る偏りがあり、全体を固定長の窓で探す方式では目的外の区間が判定を支配し得る。ただし最低音量区間が必ず雑音とは限らず、これだけで原因を断定しない。

区間抽出は低音量区間の影響を減らし、MFCC平均補正は録音経路の一定の音色差を減らす試みである。DTWは局所的な時間伸縮を許容する。一方、人声の分離、鳴き声の存在検出、DTW経路の厳密な時間制約は未解決。平均補正は識別に有用な静的音色も落とし得る。内蔵基準のラベル・切り出し範囲を人が確認する必要も残る。

マーシャドー録音は8 kHz・モノラルでの最大フレームRMSが約0.00264、RMSの20パーセンタイルとの比が約2.3だった。他12件の同比は約11.6〜229.4で、マーシャドーの音量変化は特に小さい。鳴き声がないとは断定できないが、再録音の優先候補である。

### 次の改善の優先順位

1. 独立評価データを増やす。各13匹で、別日に3〜5回ずつ、スピーカーや距離を変えたiPhoneマイク録音と、正解・機種・距離・環境・録音日を用意する。特にマーシャドー・ラプラス・ヒスイゾロアークを優先する。共有済みデータは開発用に固定し、新しいセッションを評価用に分ける。
2. 無音・人声のみ・店内雑音の録音を集め、目的の鳴き声を含まない入力の棄却と、判定不確かの閾値を評価する。現在の最大エネルギー区間抽出は人声を区別しない。
3. 基準MP3のラベルと鳴き声区間を確認し、複数のマイク録音テンプレート、log-melやデルタ特徴、DTW経路制約を同じ独立データで比較する。登録数の多いクラスに有利な最大値集約も見直す。
4. 学習済み埋め込みを使った13クラス用分類器を、セッションを分けた学習・評価で試す。今回の汎用YAMNet直接照合は5/13にとどまるため、現段階ではアプリへ組み込まない。AIが必ず改善するとは扱わない。
5. iPhone Safari実機で、マイク権限・録音形式・メモリ・待ち時間・保存・再生を確認し、標準方式を変更するか判断する。

## 現行方式の問題

- 8 kHzへ線形補間でリサンプリングする。4 kHz以上の情報を落とすうえ、アンチエイリアスのローパス処理がない。
- 64 ms窓、32 ms間隔、24個の対数間隔帯域の対数パワーをフレーム内で中心化・正規化する。MFCCではない。`log(1+power)` は小音量で音量変化に対して完全には不変でない。
- 照合は5通りの一定の速度倍率で線形対応させる。鳴き声の部分ごとの伸縮には対応しない。粗い探索間隔により一致区間を外す可能性もある。
- 3秒の窓が有効フレーム55%以上であること、3分割した各区間の有効フレーム数などを要求する。短い鳴き声＋長い無音では、正しい基準自身でも照合が成立しない。人の声も有効フレームになり、鳴き声との区別はない。
- 全候補の最大値を採用するため、登録数が多いクラスは高い最大値を得やすい。追加録音と内蔵MP3の指標も、異なる録音条件に対して校正されていない。
- 0.03の僅差表示は未校正。全候補が低品質でも相対順位が付く。未知音、人声、雑音の棄却を評価していない。
- 保存時に先頭180フレームだけを保持していた。長い区間を登録すると後半の鳴き声が失われ、使用者には分からなかった。

今回の修正は全クラス共通の2点のみ：探索グリッドから外れた末尾の候補も比較する、180フレームを超える登録区間は黙って切らずエラーを表示する。旧保存キー、旧180フレーム以内のデータ、JSON形式を維持する。過去に切り捨てた音声を特徴JSONから復元することはできない。

## 方式比較と選択

| 方式 | iPhoneブラウザでの実装 | 長所 | 検証すべき点・判断 |
| --- | --- | --- | --- |
| 現行スペクトル＋一定倍率 | 既存のWeb AudioとJavaScript | 軽量、旧データ互換 | 録音条件と局所的な時間変化に弱い。検証済みの標準方式として当面維持 |
| MFCC＋DTW | Web Audio、FFT、軽量JavaScript。実験用コードを追加 | 音色と時系列を扱う。c0を除いて音量への依存を減らし、局所的な時間対応を試せる | 人声を自動で除ける訳ではない。今回は速度変更・雑音で現行より悪化し、不採用 |
| log-mel＋DTW／デルタ特徴 | 同様に実装可能 | MFCCで捨てる帯域詳細や変化率を比較できる | ラベル付き録音を揃えた後の次候補。旧特徴だけから正確には再生成できない |
| 音声埋め込み（YAMNet等） | TensorFlow.jsまたはONNX Runtime Web。モデルの配信とSafari検証が必要 | 録音条件に対して頑健な表現を得られる可能性 | 一般環境音モデルはポケモン13種を学習していない。音声モデルの選択、クラス用の学習・評価、配信容量、メモリ、起動時間を測定する必要がある |

現実的な最初の評価候補は小規模なMFCC／log-mel＋DTWで、ニューラルモデルへの移行は独立録音の比較結果で決める。`tools/mfcc-dtw.js` は評価専用で、アプリから読み込まない。8 kHz、25 ms窓、10 msホップ、24三角melフィルタ、c0を除く13係数、正規化、端の低エネルギー区間の除去、部分系列DTWの試作である。経路の時間長制約や複数テンプレートの集約は未校正であり、本番利用の完成版ではない。

## 必要な実録音と評価方法

原因分析の開始には各クラス3〜5回の独立したマイク録音（計39〜65回）を用意する。特にアルセウスとマーシャドーの誤判定例と正解例を含める。方式選択・最終評価の次の目安は13匹×20回＝260回の独立したiPhoneマイク録音。各クラス5回をテンプレート、5回を開発検証、10回を最終テストとし、録音セッションを分ける。同じ録音の切り出し違いや加工違いをテンプレートとテストに分けない。全クラスで同じ手順・同じ条件数を使い、アルセウスだけを特別扱いしない。実際のプレイ環境で鳴き声を再生し、静かな環境、通常の周囲音、人声混入、距離・音量を変えた条件を含める。さらに鳴き声なし・人声のみ・環境音のみを各10回以上採取し、誤受理率を測る。件数は開始時の目安で、高精度を保証する条件ではない。

ファイルには正解名、録音ID、iPhone機種、iOS、マイク/画面録画の別、日時またはセッションID、再生元、距離、録音環境、鳴き声の開始・終了秒を対応付ける。画面録画の元ファイルは基準の確認用にも使う。旧追加録音JSONは現行方式の分析に利用できるが、MFCCや音声埋め込み用には元のM4A/WAV/MP4が必要である。

外部録音の評価用manifest例（データはリポジトリ外に置く）：

```json
{
  "recordings": [
    {"id":"arceus-ref-01","name":"アルセウス","session":"quiet-session-A","split":"reference","file":"ref-01.m4a","start":1.2,"end":3.4},
    {"id":"arceus-test-01","name":"アルセウス","session":"quiet-session-B","split":"test","file":"test-01.m4a","start":0.8,"end":3.0}
  ]
}
```

```sh
node tools/audio-evaluate.cjs /path/to/manifest.json /tmp/held-out-report.json
```

この例は形式を示す2件だけで、13種の評価として十分ではない。ツールはセッションIDと元ファイル内容のSHA-256によるテンプレート・テスト間の重複を拒否する。分割の真正性はデータ収集時に確認する必要がある。複数テンプレートはクラス内の最大値で評価する（現行と同じルール）。外部参照は現行の登録形式と同じ180フレーム以内に区間を指定し、丸め処理も揃える。開発検証と最終テストは別manifestで実行し、最終テスト結果で閾値を調整しない。全体正解率だけでなく、クラス別正解率、混同行列、棄却数を確認する。今回のツールは13種の閉集合の評価用であり、未知音の棄却評価や実機の遅延評価は次の段階で追加する。

## 次の優先順位

1. 画面録画を聞いて基準13本のラベル・区間を確認し、上記の実マイク録音を集める。アルセウス→マーシャドーの誤判定ファイルは、正解例と同じ条件で比較する。
2. データをセッションで分割し、クラス別・混同行列の基準値を確定する。開発用データで僅差・最低指標・鳴き声なしの棄却閾値を校正する。
3. 全クラス共通のアンチエイリアス、鳴き声区間抽出、MFCC/log-mel＋制約付きDTWを比較する。登録数の偏りに強いテンプレート集約と、長い録音・人声混入の扱いを検証する。改善しない方式を標準にしない。
4. 独立した録音で改善した方式をWeb Worker化し、iPhone Safariで初期化・録音・メモリ・判定時間を測る。旧データは残し、新特徴が必要な録音には再登録導線を用意する。
5. 上記方式の精度が不足する場合に音声埋め込み＋クラス用分類器を比較する。単純方式とのクラス別精度・棄却・実機負荷の差で採否を決める。

今回は「iPhoneで高精度に完成」とは言えない。再現可能な評価と2件の既知不具合修正が完了した段階であり、実録音が届いた後に独立録音の評価を継続する。現在のマイク録音1件は方式選択に使用した開発ケースであり、全13種の独立評価は未完了である。

## 共有された登録サンプルの診断

ユーザーからアルセウス1件のv8.6登録JSONを受け取った。形式は正常で、93フレーム（約3.008秒）。RMSの最小値0.00017、中央値0.0004、最大値0.00333である。同じ特徴データ自身との自己照合も不成立だった。完全一致の対応では、query閾値0.00025以上のフレームは56個だが、reference閾値0.0003も満たすフレームは52個で、必要な53.94個に届かない。重み総和は18.28で、必要な13.95を超える。別の倍率・位置の候補にも各種条件があるため、この数値だけで全候補の棄却理由を代表することはできない。

診断用に特徴ベクトルをそのまま保持しRMSだけを10倍すると、自己照合は指標約1.000で成立する。この実験は固定の音量条件の影響を示すが、元音声を増幅して特徴を再抽出した実験ではない。閾値の無条件緩和や、アルセウス専用処理は行わない。登録データに自己照合チェックを表示し、不成立のサンプルの再録音・区間見直しを促す。既存データは変更・削除しない。自己照合の成功を別録音への正解率と混同しない。

登録サンプルの特徴を入力として内蔵13本と比較すると、アルセウス0.268、マーシャドー0.248で僅差だった。この入力はスクリーンショットの判定に使ったマイク録音ではなく、登録された約3秒の特徴である。

再現には `node tools/diagnose-samples.cjs /path/to/samples.json` を使用できる。共有されたJSONそのものや特徴ベクトルはGitHubに追加していない。

誤判定の入力はYouTube `https://youtu.be/D9Wb87mEp04` の0〜2秒をiPhoneマイクで録音したものとの回答を得た。YouTube原音は実際のマイク録音を再現するものではない。YouTube取得はネットワークプロキシの403で未実施。この時点では入力の元M4A/WAVなどが未共有で、録音の比較が必要だった。その後受け取ったM4Aの検証結果を次節に記載した。

## 誤判定したマイク録音による再現と補正実験

ユーザーから `frienda-recording.m4a` を受け取り、ヌメルゴン1位・アルセウス5位・追加録音不成立をブラウザーで再現した。ファイルは48 kHz・2チャンネル・コンテナ長7.404秒で、Chromiumのデコード後は約7.359秒だった。44.1 kHzデコードではヌメルゴン0.565、サザンドラ0.466、アルセウス0.222。48 kHzデコードでも同じ順位（ヌメルゴン0.563、アルセウス0.220）になった。スクリーンショットの数値と完全一致ではないが誤判定の順位と追加録音不成立を再現した。

左チャンネルのRMSは約0.0124、右は約0.000000844で、右はほぼ無音だった。既存の平均化でモノラルのRMSは約0.00620になる。しかし左チャンネルだけで比較してもヌメルゴン1位であり、ステレオ平均化だけが誤判定の原因ではない。録音の低音量区間を選んでもヌメルゴンへの指標が高くなった。自動判定は約3.84〜6.85秒を採用し、その後半は低音量である。波形では主な大音量区間が約0〜0.6秒と約2.8〜4.4秒にあったが、大音量であることだけでは鳴き声か人声かを決められない。

入力と登録特徴のRMSを各々の90パーセンタイルで補正する診断でも、ヌメルゴンが1位のままで、追加録音のアルセウス指標は約0.105にとどまった。単に音量条件を緩めるだけでは今回の誤判定は解決しない。MFCC＋DTW試作は録音全体をディアルガと判定した。

次の候補として、正規化済みMFCC特徴の時間平均を引き、再正規化してDTWで比較する補正を評価専用に追加した（厳密な未正規化ケプストラムのCMNとは異なる）。録音全体ではアルセウスが1位になったが、このデータを見ながら方式を選んだため、開発ケースとして扱い、独立テストの精度に数えない。

## 学習済み音声AIの比較準備

`tools/yamnet-evaluate.py` を追加した。公式YAMNetの1024次元埋め込みを抽出し、内蔵13本の埋め込みとのコサイン照合を比較する評価専用ツールである。521種の一般音声イベント分類出力をポケモンのラベルと見なすことはしない。13種の分類器の追加学習はまだ行っていない。16 kHz・モノラル化はFFmpegを使い、全フレームの平均と音声エネルギーによる重み付き平均の2方式を固定して比較する。期待ラベルで区間やパラメーターを変えない。

公式ソース： https://github.com/tensorflow/models/tree/34a21326906b9574fa11c4d6d0a5c534ff039267/research/audioset/yamnet

公式重み： https://storage.googleapis.com/audioset/yamnet.h5

当初の検証状況（後に取得・評価完了）：TensorFlow CPU 2.20.0とtf-keras 2.20.1をリポジトリ外に導入し、公式ソースから3,751,369パラメーター・1024次元出力のモデル構築を確認した。公式重みの取得はネットワークプロキシの403でブロックされ、学習済みモデルの推論・精度比較は未実施。ランダムな初期重みで判定結果を作ることはしない。評価CLIは重みがなければ失敗し、精度レポートを生成しない。`storage.googleapis.com` の追加を環境設定ドラフトに保存したが、それだけでは実行環境への適用を証明しない。

再現手順（アプリの依存関係や保存データを変更しない）：

```sh
python3 -m pip install --target /workspace/shared/yamnet-python --cache-dir /tmp/frienda-pip-cache tensorflow-cpu==2.20.0
# TensorFlow CPUが同じtensorflowモジュールを提供するため、tf-kerasから別のtensorflow配布を重複導入しない。
python3 -m pip install --target /workspace/shared/yamnet-python --cache-dir /tmp/frienda-pip-cache --no-deps tf-keras==2.20.1
mkdir -p /workspace/shared/yamnet-source
for yamnet_source_file in yamnet.py params.py features.py; do
  curl --fail --location "https://raw.githubusercontent.com/tensorflow/models/34a21326906b9574fa11c4d6d0a5c534ff039267/research/audioset/yamnet/${yamnet_source_file}" -o "/workspace/shared/yamnet-source/${yamnet_source_file}"
done
# 信頼できる公式HTTPS経路から yamnet.h5 を取得する。TLS検証を無効にしない。
curl --fail --location https://storage.googleapis.com/audioset/yamnet.h5 -o /workspace/shared/yamnet-source/yamnet.h5
PYTHONPATH=/workspace/shared/yamnet-python python3 tools/yamnet-evaluate.py /path/to/development-manifest.json --yamnet-dir /workspace/shared/yamnet-source --output /tmp/yamnet-report.json
```

manifestは既存評価ツールと同じ `purpose=development`、各録音の `id/name/file/split=test` を使う。このAI試作は録音全体のみを比較し、区間指定や外部学習テンプレートはまだ対応していない。公式モデルのソース・重みのSHA-256、入力ファイルのSHA-256、各方式の上位候補を記録する。元音声や埋め込みそのものはレポートに出力しない。iPhoneブラウザでの推論速度・メモリ・TF.js変換はまだ検証しておらず、このPython評価をアプリに組み込んだとは扱わない。
